在智语言“中文为形”的核心设计下，所有用户可见的标识符、方法名、参数名均需使用中文。处理无法直译的英文技术术语时，遵循以下策略。以下策略做法更多是把英文术语在代码层面上做了隐藏，保证了代码风格的统一性，并没有翻译，也没有直接使用不好翻译的英文术语，同时在口语与文档描述上保留了英文术语，保证了交流与理解的一致性。

---

### 两类问题的区分

**代码层面（API 表面）**：函数名、参数名、变量名、结构体名、字段名写出来给编译器看，必须全中文。把英文术语在代码层面做隐藏，保证代码风格的统一性，不好翻译的英文术语并没有翻译，也没有直接使用。

**口语/文档层面**：开发者在交流、写注释、写文档时，保留了不好翻译的英文术语，保证交流与理解的一致性。

当前策略主要解决的是**代码层面**的问题——让术语不出现在代码层面（API 表面）上，保证代码风格的统一性。口语和文档中的术语使用，遵循“能用中文就用中文，技术文档解释必要时保留英文术语作为精确指代”的原则。


   ### 策略一：英文术语参数化

   **核心思想**：英文术语**降级为数据**。函数名、参数名全部使用中文，只有参数**值**位置出现英文术语。

   **三种落地形式**：

| 形式                | 说明                                   | 案例                                   |
| :------------------ | :------------------------------------- | :------------------------------------- |
| **字符串参数**      | 术语作为字符串值传入                   | `工具.哈希算法("MD5", 数据)`           |
| **结构体/对象参数** | 通过中文结构体包装，内部属性接收术语值 | `数据压缩.压缩("gzip", 原始数据)`      |
| **枚举化**          | 术语映射为枚举成员，编译期类型检查     | `工具.计算哈希(哈希算法.SHA256, 数据)` |

   **适用场景**：操作对象属于**开放、持续增加**的标准列表，如加密算法、编码方案、数据格式。

   **已有实践**：

   ```智语言
   工具.哈希算法("MD5", 数据)
   工具.解析数据("JSON", 文本)
   工具.编码方案("BASE64", 数据)
   ```


   ### 策略二：英文术语行为抽象化

   **核心思想**：英文术语**完全消失**。将术语所代表的行为或能力抽象为纯中文函数/方法名。用户只看到“做什么”，不需要知道底层“用什么技术做”。

   **两种落地形式**：

| 形式             | 说明                             | 案例                                      |
| :--------------- | :------------------------------- | :---------------------------------------- |
| **通用行为抽象** | 术语隐藏在通用中文动词/名词中    | `网络.获取(网址)` 隐藏 HTTP GET           |
| **领域驱动命名** | 按业务职责命名，不按技术术语命名 | `内存缓存.获取(键)` 而非 `Redis.获取(键)` |

   **适用场景**：描述**通用行为或抽象能力**，如网络协议、并发模型。

   **已有实践**：

   ```智语言
   网络.获取(网址)                    // 隐藏 HTTP GET
   网络.启动服务(端口, 处理器)        // 隐藏 HTTP Server
   网络.设置会话凭证(名称, 值, 选项)  // 隐藏 Cookie
   ```


   ### 策略三：英文术语约定规范化

   **核心思想**：术语不消失，但通过**模块名提供上下文**和**社区映射表**来消化。

   **两种落地形式**：

| 形式             | 说明                             | 案例                                     |
| :--------------- | :------------------------------- | :--------------------------------------- |
| **约定优于配置** | 模块名承担术语含义，函数名更简洁 | `并发.启动任务` 而非 `并发.启动协程`     |
| **术语映射表**   | 维护官方/社区的中英文映射规范    | `HashMap → 映射`、`Thread Pool → 协程池` |

   **适用场景**：跨模块通用概念命名，新术语引入时的标准化。

   **已有实践**：

   ```智语言
   并发.启动任务(操作)     // 模块名“并发”消化了 goroutine/coroutine
   网络.连接(地址, 端口)    // 模块名“网络”消化了 TCP
   网络.监听(端口, 选项)    // 模块名“网络”消化了 TCP Listener
   ```


   ### 策略四：英文术语标识符命名

   **核心思想**：变量名、参数名、结构体名、字段名等**标识符**全部使用中文，不出现英文术语。

   **三种递进方法**：

| 方法               | 核心逻辑                   | 适用场景             | 示例                                         |
| :----------------- | :------------------------- | :------------------- | :------------------------------------------- |
| **字面翻译中文化** | 直接翻译英文单词           | 有明确中文对应词     | `地址` ← address、`端口` ← port              |
| **含义描述中文化** | 描述这个数据**是什么**     | 术语直译后含义模糊   | `来源地址` ← sourceAddress、`字节数` ← count |
| **行为结果中文化** | 描述这个数据**用来做什么** | 抽象概念、状态、凭证 | `会话凭证` ← Cookie、`状态码` ← statusCode   |

   **选择优先级**：优先字面翻译 → 翻译有歧义时描述含义 → 抽象概念时描述行为结果。

   **已有实践**：

   ```智语言
   // 字面翻译中文化
   文本 地址              // address → 地址
   整数 端口              // port → 端口
   
   // 含义描述中文化
   整数 字节数            // count → 字节数
   文本 来源地址          // sourceAddress → 来源地址
   
   // 行为结果中文化
   会话凭证               // Cookie → 会话凭证
   状态码                 // statusCode → 状态码
   ```


   ### 四大策略速查表

| 策略               | 核心思想                      | 处理对象                   | 术语在 API 表面的位置 | 典型用例                        |
| :----------------- | :---------------------------- | :------------------------- | :-------------------- | :------------------------------ |
| **术语参数化**     | 术语降级为参数**值**          | 函数/方法调用的实参        | 参数值位置            | `工具.哈希算法("MD5")`          |
| **术语行为抽象化** | 术语完全**隐藏**              | 函数/方法的名称            | 完全消失              | `网络.获取`（隐藏 HTTP GET）    |
| **术语约定规范化** | 术语通过上下文/映射表**消化** | 模块名、社区规范           | 模块前缀或映射表中    | `并发.启动任务`、`HashMap→映射` |
| **术语标识符命名** | 术语被中文名称**替代**        | 变量、参数、结构体、字段名 | 完全消失              | `来源地址` 而非 `sourceAddress` |


   ### 代码之外：口语与文档中的术语

   四大策略解决了代码“怎么写”的问题。但在**开发交流、文档撰写、注释说明**中，如何处理术语？

   **原则**：能用中文就用中文，必要时保留英文术语作为精确指代。

| 场景                     | 处理方式                | 示例                       |
| :----------------------- | :---------------------- | :------------------------- |
| **有公认中文译名**       | 使用中文译名            | “超文本传输协议” 或 “HTTP” |
| **无公认译名但概念清晰** | 使用中文描述 + 英文注释 | “数据报通信（UDP）”        |
| **需要精确指代技术实现** | 直接使用英文术语        | “调用 BLAS 库进行矩阵运算” |
| **社区通用缩写**         | 中英混用，中文为主      | “REST API”、“JSON 格式”    |


   ### 核心指导原则

   1. **API 表面中文化**：函数名、参数名、变量名、结构体名、字段名全部中文。术语只出现在参数值位置或完全消失。
   2. **标识符见名知意**：名字应让读者一眼理解其存储内容的含义。
   3. **优先字面翻译，其次含义描述，最后行为结果**：标识符命名时从简单到高级递进选择。
   4. **能用模块消解，不用冗长前缀**：`并发.启动任务` 而非 `并发.启动协程`。
   5. **能按职责命名，不按技术命名**：`内存缓存.获取` 而非 `Redis.获取`。
   6. **能约定统一，不各自为战**：用映射表规范社区，而非各人随意起名。
